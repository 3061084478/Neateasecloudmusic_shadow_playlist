# Shadow V5 话题交接文档

## 1. 文档目的

这份文档用于把本轮关于 `Shadow V5` 的主要讨论、已做改动、已确认方向、踩坑记录和当前停留状态交接给其他开发线或后续接手者。

文档时间基线：`2026-05-03`

---

## 2. 项目当前大方向

本项目已经明确收口为：

- 架构：`桌面壳 + 内嵌本地 Web 前端(dist) + 本地 bridge/backend`
- 正式路径：`MainWindow -> 单个 WebShellPage -> 单个长期存活的 QWebEngineView -> React App`
- 登录启动页和登录后主界面：都放在同一个 Web 前端场景里完成
- 不采用正式 `localhost` 启动模式
- Python / Qt 只负责：
  - 窗口
  - WebView
  - bridge/backend
  - 启动与业务控制
- React / Web 负责：
  - 登录页视觉
  - 启动到主页转场
  - 主壳导航
  - 页面内容呈现

## 3. 本轮对外观与交互的主线要求

### 3.1 登录后主界面壳层

用户目标不是“按钮改样式”，而是重做登录后整体 Shell：

- 顶部导航、好友侧栏、主工作区形成统一的“切片式高级桌面壳”
- 切换页面时要有“中翻页 / 桌面式层叠翻页”感
- 子功能页切换时也要带切片翻页感
- 保留现有 logo、路由、好友数据流、设置接口和 PySide6 只负责外壳的架构

用户曾连续提出过这些 UI 调整点：

- 去掉 logo 外框
- 去掉右上角“展开任务栏 / 刷新当前页”外框
- 去掉页面里的 `Workspace` 文案
- 让导航背景框不要过大，只比导航内容略大即可
- 提示词浮层要永远在最顶层，不能被切页切片盖住
- 下拉、筛选、日期表必须出现在顶层，且鼠标命中优先在浮层上
- 没有内容时就不要出现多余的占位点或句号

### 3.2 全站信息层级

曾明确制定过“全站字体与颜色主次系统”：

- 建立 `L1 ~ L5` 文字层级
- 主文本、次文本、辅助文本、元信息、操作强调分层
- 强化“操作与结果”，弱化“占位和技术小字”
- 重点改歌曲分享、聊天记录、影子歌单 command panel
- 重构首页入口卡、结果流、好友栏、音乐关系页 KPI/图例/总结的层次

后续还补了一条细规则：

- “没有内容就没有内容，不要出现那个 `.` 或无意义占位”

### 3.3 背景氛围

背景方向被明确锁定过几轮：

- 基础背景：右上到左下的白色扩散体积雾光
- 风格：高级官网 / 摄影棚空气感
- 动态：极轻微，必要时可以静态化

之后加入过蝴蝶背景线，并且多次反复精修：

- 一开始是“白色微型蝴蝶粒子”
- 后来改成更真实的写实蝴蝶
- 最后收口为“少量顺光蝴蝶 + 更柔的体积雾束”

最终用户偏好收口为：

- 只保留少量蝴蝶
- 围绕光束边缘分布
- 主蝴蝶不要太抢
- 逆光边缘要克制
- 更像真实瞬间，不像设计摆拍

用户后来又要求：

- 删掉第四只，只保留三只
- 三只大小依次递减
- 第一只位置多次微调

注意：这条蝴蝶背景线在后续回退前曾被大量改动，但目前代码已经回退，不应默认认为这些效果还在当前代码中。

### 4.2 音乐关系首页与“我的音乐社交”

用户重新定义了“歌手总览”逻辑，不再围绕风格：

#### 首页改法

- `共同内容` 改成：`共同歌手：***`

  - 左：我发给好友的歌曲里的歌手 Top5
  - 中：双方发歌总计歌手 Top3
  - 右：好友发给我的歌曲里的歌手 Top5

  - 是否有共同歌手
  - 我与好友分别发了多少歌

- `共同风格：暂无` 直接删掉
- 关系总览页里改为：
  - 好友的分享歌手 Top1
  - 然后才是共同歌手 Top2，没有就是暂无

#### 我的音乐社交页改法

- `整体风格音乐社交整体风格与歌手` 直接改为 `歌手总览`

  - 我发给所有好友的歌手总计 Top5
  - 我发给好友们的歌手和好友们发给我的歌手的交集 Top5
- 如果交集没有：显示 `暂无共同歌手`

#### 交互联动要求

用户要求“歌手交集概况”做强联动动态：

- “我的分享”卡 hover 时，联动交集左块
- “好友的分享”卡 hover 时，联动交集右块

- 交集右块 hover 时，联动“好友的分享”
- 交集中心块 hover 时，联动下方颜色条和交集歌手卡
- 歌手块 / 颜色块 / 中心块三者需要联动

#### 额外要求

- 音乐关系总览页增加“我”的信息卡
- 结构类似好友卡片，包含：
  - 头像
  - 名字
  - 社交标签
  - 我最爱分享的歌手

注意：这些业务需求在这条线上被明确讨论过，但本次回退后不代表当前代码都已处于最终完成态，需要结合实际源码再确认。

## 5. 归档 / 全好友归档 / 游标方案讨论

### 5.1 问题背景

用户发现：

- 如果朋友给自己发歌，但自己没主动查询该好友歌曲
- 这些记录可能没有及时纳入统计
- 导致统计总数不真实

### 5.2 讨论结论

讨论过几种方案：

#### 方案 A：每次都同步增量

- 风险：担心卡顿

#### 方案 B：全量重建归档

- 用户认为如果每次都从头跑太浪费

#### 方案 C：双游标推进

用户提出较明确方案：

- 每个好友维护两个游标：
  - 歌曲游标
  - 聊天游标
- 主动查询某个好友歌曲或候选时，歌曲游标前进
- 主动查询聊天记录时，聊天游标前进
- 游标不后退
- `全好友归档` 时：
  - 从每个好友当前游标位置往后推进
  - 直到没有新内容为止
  - 然后更新游标
- 如果第一次使用，游标在起点，那么第一次 `全好友归档` 本质上就等于全量归档

### 5.3 UI 要求

用户要求在音乐关系页标题行最右边：

- 在 `刷新分析` 左边增加 `全好友归档` 按钮
- 样式和 `刷新分析` 保持一致

### 5.4 “全量归档”是否保留

用户后续判断：

- 如果 `全好友归档` 已经是“从游标推进到终点”的升级版
- 第一次使用时它自然也等于全量归档
- 那么旧的 `全量归档` 可能没有必要继续保留

### 5.5 探测页数策略

用户还追问过：

- 为什么默认只探测每个好友 `1` 页最新消息可以快速判断游标是否已到前沿
- 为什么以前设置的是 `6`

后续决定方向为：

- 给 `全好友归档` 单独使用 `1 页探测模式`
- 把 `6` 留给聊天 / 歌曲查询自己的翻页策略

## 6. 登录启动页与单 Web 场景重构主线

### 6.1 用户目标

用户明确不想要“Qt 启动页 + Web 主界面”的割裂体验，而是：

- 登录前后放在同一个 Web 场景中
- 登录成功后：
  - 启动页元素沉入背景
  - logo 浮现
  - 蝴蝶渐显
  - 主界面模块像从背景里冒出来

### 6.2 启动页视觉剧本

用户多轮确认过的镜头语言：

1. 一束光从右上射向左下
2. 这束光先有“射入”的入场动画
3. 射入结束后变暗、变宽，成为背景常驻光束
4. `Shadow` 从黑暗里慢慢往上钻出
5. 钻出过程中被斜向光逐步照亮
6. `Shadow` 露出后上移，让出中心位置
7. 中央两个按钮从黑暗中“后翻到前”
8. 如果需要二维码，二维码像实体卡片从暗处翻到正面

用户不想要的效果：

- 机械线性慢推
- 普通淡入淡出
- 普通 `opacity + translateY` 就算翻出
- 额外解释文案过多
- `Shadow Playlist`，只保留 `Shadow`

### 6.3 单窗口 / 单 WebView / 单前端场景

本条线上已经做过的重构方向：

- `MainWindow` 只持有一个主窗口
- `WebShellPage` 只持有一个长期存活的 `QWebEngineView`
- 登录启动页和主界面全部由前端 `App.tsx` 内部状态机控制
- 旧 Qt 启动页链路已经被计划性废弃

## 7. 黑闪、黑边、标题黑框问题线

### 7.1 用户现象

用户持续反馈过这些问题：

- 启动页和切换中出现黑色闪动
- 拖动窗口时会闪
- 录屏时更容易闪
- `Shadow` 标题像被一个黑色矩形框住
- 标题周边像有黑色背景板
- `s / w` 边角像被裁掉
- 按钮不像“翻出来”，而是“直接生成”

### 7.2 讨论中的技术判断

这条线上反复得出的判断是：

#### 前端层面

- 标题黑框感大概率来自：
  - 多层叠字
  - `clip-path`
  - `background-clip: text`
  - `mix-blend-mode`
  - 大面积 `text-shadow`
- 按钮表面细黑线来自：
  - 为了模拟厚度而增加的伪元素层

#### Qt / WebEngine 层面

- 黑闪并不一定来自页面还在动
- 即使背景和 3D 动画已经静止
- `QWebEngineView` 在 Windows 下遇到这些情况仍可能闪：
  - 拖动窗口
  - 切出焦点
  - 桌面录屏捕获
  - DWM / GPU surface 重组

换句话说，闪动往往是桌面合成链问题，不等于业务逻辑仍在执行动画。

### 7.3 本线曾尝试过的止闪方向

曾经做过或尝试过这些方向：

- 统一 Qt / WebView / body / app-shell 背景色
- 去掉大量动态 `blur/filter`
- 关闭 `WA_OpaquePaintEvent`
- 尝试更温和的启动标题光效
- 尝试给 `main.py` 加 Windows 下的止闪启动参数

但这些止闪与启动页细修发生在本条线上较晚阶段，后来已经被整体回退，不能默认还保留在当前代码。

## 10. 交接给别的线时最该知道的坑

### 10.1 `dist` 不会跟 Git 一起回退

这是本次最关键的坑。

- `web/dist` 被忽略
- 切换提交后如果直接运行，很可能前端还是旧的或新的残留产物
- 必须重新跑：

```bash
cd V5/web
npm run build
```

### 10.2 黑闪不一定是页面动画本身造成

用户多次误以为：

- “光束已经停了，为什么还闪”

这条线上的技术判断是：

- 黑闪很多时候是 `QWebEngineView + Windows DWM + GPU/录屏/拖窗` 的合成问题
- 不等于页面逻辑仍在动

### 10.3 标题黑框问题很容易被“文本特效层”放大

`Shadow` 标题如果再采用这些手法，极容易再次触发类似问题：

- `clip-path`
- `background-clip: text`
- 多层叠字
- 大面积 `mix-blend-mode`
- 很重的阴影

### 10.4 用户对质感要求非常高

用户不是只要“能用”：

- 很在意是否像“真实电影镜头”
- 很在意是否“浮在背景上”
- 很在意“不要被框住”
- 很在意“不要 UI 感太重”

所以视觉实现不能只靠普通 fade / slide 替代。

## 11. 如果后续继续推进，建议顺序

建议后续接手按这个顺序推进：

1. 先确认当前 `6be4866` 对应版本是否能稳定运行
2. 再确认当前版本下：
   - 登录页长什么样
   - 主界面长什么样
   - bridge 和前端是否完全匹配
3. 若继续做启动页：
   - 优先保持单 Web 场景主链
   - 不要回退到 Qt 原生启动页
4. 若继续修黑闪：
   - 分清“前端视觉问题”和“WebEngine 合成问题”
   - 不要把两类问题混在一起判断
5. 若继续做 UI 电影感：
   - 标题尽量用更稳定的单层或少层方案
   - 避免重度 `clip-path` 和复杂混合模式
6. 若再切换提交或回退：
   - 必须重建 `web/dist`
